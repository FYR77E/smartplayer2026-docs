# SmartPlayer Docs Design Contract

## Цель
Эта документационная платформа должна ощущаться как зрелый продуктовый слой SmartPlayer, а не как набор разрозненных справок.

Главные поверхности:
- `Главная` — маршрутизатор сценариев
- `Пошаговый старт` — линейный сценарий первого запуска
- `Интерактивный тур` — короткий визуальный walkthrough
- `Чек-лист перед запуском` — финальная сверка перед пилотом или rollout
- `Полная документация` — канонический reference-слой

## Принципы
- Не делать глобальный редизайн без явной причины.
- Полировать текущую платформу, а не изобретать новую концепцию.
- Каждый экран должен помогать пользователю принять следующее действие.
- Визуальная выразительность допустима, но не ценой UX-ясности.
- Любой secondary UI не должен конкурировать с главным действием текущего шага.

## Визуальный язык
- Тёплая нейтральная база, а не холодный SaaS-default.
- Акцентный цвет используется экономно и только для направления внимания.
- Избегать generic-ощущения через слишком стандартные композиции, но не скатываться в декоративность.
- Не использовать фиолетовый как дефолтный акцент.
- Не использовать «карточки внутри карточек внутри карточек», если это не оправдано задачей.

## Типографика
- Заголовки должны быть короткими, с сильной иерархией.
- Intro-copy, completion-copy и CTA-copy должны быть компактнее, чем кажется комфортным в черновике.
- Избегать технического жаргона в пользовательских entry points:
  - не писать `standalone`
  - не писать `reference-version`
  - не писать `launch gate`
  - не писать `rollout`, если можно сказать по-русски
- Тон: спокойный, уверенный, продуктовый, без маркетинговой накачки.

## CTA-иерархия
- На каждом экране должен быть один главный CTA.
- Secondary CTA допустим, если он не размывает основной маршрут.
- Exit / back / restart — поддерживающие действия, а не конкурирующие primary.
- После завершения сценария пользователь должен видеть явный следующий путь.

## Interactive Tour
- Сохраняем концепцию screenshot-tour.
- Не возвращаем Driver.js.
- Подсветка должна совпадать с описанием шага, а не просто «примерно попадать в блок».
- Если исходный скриншот шумный, сначала пробуем решать это на уровне визуального слоя тура, не ломая source-assets.
- Popover не должен перекрывать highlight.
- Step chips должны быть реальной навигацией, а не декоративным прогрессом.
- Активный step chip должен оставаться видимым на узких экранах.
- Текущий шаг должен читаться даже тогда, когда progress header уже ушёл выше fold.
- На mobile сценарий читается как guided reading flow, а не как стек кнопок.

## Quick Start
- Это полный линейный сценарий со скриншотами.
- Он не должен путаться с краткой docs-версией быстрого старта.
- После Quick Start должен быть естественный handoff в checklist.

## Completion State
- Completion screen — это handoff, а не финальный тупик.
- На completion должны быть явно видны следующие 1–2 шага.
- Restart должен быть поддерживающим действием.

## Mobile
- На узких экранах сохраняем смысл, а не desktop-плотность.
- Убираем дублирующую навигацию и второстепенный шум.
- Вертикальный ритм должен быть плотнее, но не тесным.
- Основные действия должны появляться раньше второстепенных.

## Что избегать
- Избыточных поясняющих блоков перед действием.
- Нескольких равносильных CTA рядом.
- Смешения product copy и внутренних терминов команды.
- Повторения одного и того же смысла в hero, intro и footer.
- Слишком тяжёлых first screens, где пользователь долго не доходит до действия.

## Definition of Done для polish-pass
Перед выкладкой проверяем:
- `npm run check:tour`
- `npm run check:release:full`
- desktop / medium / mobile путь для затронутого сценария
- что новый copy не ломает route smoke
- что handoff после сценария читается естественно
